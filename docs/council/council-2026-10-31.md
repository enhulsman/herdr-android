# Council: android-client-v1 (2026-10-31)

Target: `openspec/changes/android-client-v1/` (proposal, design, tasks, 9 spec folders), owner decisions in `decisions.md`.

## Council Verdict: NEEDS FIX PLAN

Not a close call. All three reviews keep the architecture: direct SSH per machine, no hub, observe-by-default viewing, answering through RPCs, a per-machine watcher, libghostty-vt with Termux as fallback. The problems are spec errors against the real core's behaviour, an alert path that can fail silently, and test order. All of them can be fixed in the spec before any code is written.

## Strategic Assessment

This is the right problem and broadly the right design (high confidence). The strongest alternative is not a different architecture but a different order: M1 agent list, then answer from a text view (`terminal.read` refreshed on status events, composer, keys row), then alerts, then the live libghostty view. Today the loop that closes the gap (alert, read, answer) lands at M3/M4, after the most expensive work. The phone foreground service and the plain ntfy topic were both rejected for good reasons. The effort is likely 150-250 h, not the stated 80-150 (low-moderate confidence). v1 as specced is closer to polished than to minimal.

## Key Findings

### 1. Doc names `herdr-android/push` and `herdr-android/push-status` are invalid
**Severity**: CRITICAL (fix is trivial)
**What**: `doc.get`/`doc.set` call `check_name` (`addr.rs:6-14`, verified). It allows only 1-32 characters of `a-z 0-9 - _ .`, starting with a letter or digit, so `/` is rejected. The names are used in `design.md:102,107,134` and `specs/alerts/spec.md:8,14`.
**Why it matters**: registration, heartbeat and watcher-follow would all fail at the first call. Alerts would be dead.
**Recommendation**: use flat names (`hdroid-push`, `hdroid-push-status`) and add a test that checks them against `check_name`. Q2 then shrinks to "is a client-claimed flat name acceptable".

### 2. The alert path can fail silently, and nothing detects it
**Severity**: MAJOR (top risk, 4x4)
**What**: (a) ntfy grants are per endpoint. A distributor reinstall, data clear or re-register mints a new topic, and deny-all ntfy answers it with 403. The watcher keeps heartbeating, so `push-status` reports healthy. (b) A new endpoint reaches the machines only the next time the phone connects, and the phone is often off the tailnet exactly when alerts matter. (c) The watcher's `connect_or_start` can autostart a fresh, empty core, or find the wrong one: socket paths depend on `HC_SESSION`, `XDG_RUNTIME_DIR`, `XDG_STATE_HOME` and `HC_SOCKET` (`paths.rs:14-46`), which differ under systemd, and launchd has no XDG at all. (d) Whether ntfy delivers a binary RFC 8291 body to the connector unchanged is unverified, and VAPID (Q5) stays open until M4.
**Why it matters**: the owner will read "no alert" as "nothing needs me" while agents sit blocked for hours.
**Recommendation**: `push-status` records the last POST's HTTP status and the time of the last successful POST. The app shows "last alert delivered hh:mm" or "failing: 403". Add a "send test alert" action that goes through the real path. Either the watcher uses a write-only ntfy token scoped to `up*`, or an anonymous `up*` write grant is chosen and stated in the spec. The watcher connects to an existing core only: session and socket come from explicit config, and it fails loudly when it sees zero terminals. Add scenarios for 403 and for registering while a machine is unreachable. Move the end-to-end push spike (VAPID, binary body) into M0/M1.

### 3. The watcher's alert rules differ from the desktop's
**Severity**: MAJOR (all three reviews flag it)
**What**: the desktop `Model::alert` (`model.rs:458-480`, `window.rs:1879-1951`) counts `error` as blocked. It treats "done" as any move from busy (working, blocked or error) to non-busy, and it suppresses sub-agents (`parent`), terminals not in a pane, and any terminal the owner is looking at. The spec uses literal blocked/done, never alerts on error, and orders error separately in the agent list. "No alerts for states present at start" drops alerts across a watcher restart. Notifications stay up after the owner answers at the desk. The 0.1.15 record has no viewer, focus or `active_at`, so the watcher cannot tell whether the owner is at the desk.
**Why it matters**: a burst of alerts per sub-agent turn plus alerts while the owner sits at the desk leads to fatigue, the channel gets muted, and the feature is dead. Errors never alert.
**Recommendation**: write a transition table with tests and put it in a shared `herdr-proto` attention module used by both the watcher and the app. Persist the last alerted turn per terminal, and on startup alert for blocked terminals that were never alerted. Add a configurable grace delay, cancelled when the terminal leaves blocked. Have the watcher send an encrypted `cleared` push. Handle `missed` events and fresh snapshots. Ask the maintainers about viewer presence or a last-input time.

### 4. Composer, keys and transport assume RPC behaviour that `herdr-core` does not have
**Severity**: MAJOR
**What**:
- `send` with `if: idle` is a precondition check. It returns `status_mismatch` immediately (`input.rs:182`, verified) and never queues.
- `terminal.keys` rejects `|` and `~`, and shift+`\` gives `\` (`keys.rs:11-45,74-78`).
- No RPC types raw text without Enter.
- `send` can block 5 s + 3 s + 5 s, longer than the desktop's 10 s default timeout (`hc.rs:344`).
- Streams, the event channel included, stall after the 256 KiB initial credit unless the client sends CREDIT (`wire.rs:23`).
- Dead-link detection is unspecified. The desktop uses ServerAliveInterval 15 / CountMax 4, and the core sends a heartbeat every 15 s.
- Frames up to 16 MiB arrive with no size check (`wire.rs:8`).

**Why it matters**: the composer fails on the first idle check, keys on the shelf do nothing, and the live view freezes after about 256 KiB of output.
**Recommendation**: use `terminal.wait` then `send{if:idle}`, or a client-side queue, with scenarios for `status_mismatch` and cancelling a queued send. Test every row and shelf key against `keys::encode`, and drop the ones it rejects or route them through direct typing. Set per-method timeouts, reporting "outcome unknown" for send/keys/interrupt. Send CREDIT on attach and event channels. Reconnect after 45 s without a frame. Reject oversize frames before allocating. Tolerate shell-rc output before the first JSON line.

### 5. The size and reattach rules do not hold
**Severity**: MAJOR
**What**:
- A non-observe viewer stores its attach size. Every DATA/RESIZE/FOCUS makes it leader and reapplies that size and its display facts (`viewers.rs:44-50`). If the Mac resizes after the phone attaches, the phone's next keystroke snaps the terminal back and the Mac reflows, and theme-query answers may flip.
- The observe view has no rule for `size` events. Redraw bytes can arrive before or after the event, which garbles a stale grid.
- Every reattach sends a full first paint, so "no duplicate first paint" cannot be met.
- 0.1.16 (shipped today) changes FACTS handling. The compatibility check accepts any generation-1 core.

**Recommendation**: in direct typing, follow size events and send RESIZE with the current size before each burst. Consider `resumed:true` until the first keystroke. In observe, on a size event resize the local VT and reattach, and discard the VT on any reattach. Reword the requirement to "no stale content". Add tests for "Mac resizes during direct typing" and a mid-stream size change. Run the protocol suite against both the pinned version and latest. Warn and disable direct typing when the core is newer than the tested version. As a runtime check, read the terminal size after an observe attach and report if the desk size changed.

### 6. Release signing and the phone key carry more trust than the spec controls
**Severity**: MAJOR (two reviews flag it, and it sits on the owner's supply-chain threat model)
**What**:
- The protected environment gates *when* the signing job runs, not *what* it runs. Anyone who can push a tag (for example a dirty WSL with git credentials) can change the workflow, and the approval screen shows no diff.
- The spec requires no Cargo.lock, Gradle verification or cargo-deny.
- `herdr-push` binaries run on dev machines without checksums.
- The Keystore key has no user-authentication binding, so an unlocked phone is a shell on both machines (`machine.exec` makes the key shell-equivalent, `design.md:58-63`).
- `restrict,command=` works only under OpenSSH. WSL runs OpenSSH (verified, mirrored networking), but the Mac's sshd is unverified, and Tailscale SSH would ignore `authorized_keys` entirely.

**Recommendation**: the sign job runs only a pinned `apksigner` on an artifact built from the approved SHA: no checkout, no repo scripts. Allow only protected `v*` tags (ruleset) and protect workflow files. Lock dependencies and add verification metadata plus cargo-deny/audit. Publish checksums for `herdr-push`. Add a scenario proving a non-herdr command is refused on each machine. Key authentication (`setUserAuthenticationRequired` or an app lock) is the owner's decision, because it limits background reconnects. Escape the forced-command quoting from `machines.rs:~219` and test it against real sshd.

### 7. The spec gets the shape of the core's data wrong
**Severity**: MAJOR
**What**: the layout uses an untagged `Content` enum and a tagged `Kind` (`layout.rs:10-31,272-291`) and includes Mod panes, so strict serde rejects the whole doc on one unknown node. "Focused pane" for spaces lives in `view.json` (`mirror.rs:38-60`), not in the shared doc.
**Recommendation**: parse leniently per tab and node (`serde_json::Value`, skip unknown nodes), with scenarios for a mod pane, an unknown node and a malformed tab. Use a deterministic focus rule: first terminal pane in tree order, preferring blocked or unseen-done.

### 8. Acceptance criteria that cannot be tested
**Severity**: MAJOR
**What**: M2.2 calls for "screenshot comparison with the Mac at equal size" (GPUI against Compose pixels). Design renders cannot serve as Roborazzi goldens. The 60 fps and 200 ms scenarios give no method or device. The source of "last known screen text" is undefined: a stitched `terminal.read` with `lines>0` scrolls the live app and repaints other viewers (`stitch.rs`, `viewers.rs:97`).
**Why it matters**: under tests-first, a scenario that cannot become a test blocks its milestone.
**Recommendation**: use cell-grid goldens from synthetic fixtures, then Roborazzi goldens after one human sign-off. Measure p95 frame time with Macrobenchmark on the Pixel. Define the instant-open cache as local VT state, including its encryption and wipe. Selection uses local scrollback or `lines=0`.

### 9. The riskiest assumptions are tested last
**Severity**: MAJOR
**What**: Q3 (russh + Keystore) is tested in M1, Q4 (libghostty on the device, 60 fps) in M2, the push path in M4. The design has no plan for moving per-frame data across uniffi (RustBuffer copy per call at 200x60 @ 60 fps; moderate confidence). If Q3 falls back, the key type changes mid-plan.
**Recommendation**: in M0, run a device smoke test: load the `.so` on the Pixel, feed it recorded Claude Code bytes and draw a static frame. Also in M0, spike russh with Keystore signing and push end to end. Put the key type in the spec once Q3 is resolved. In `design.md`, write that uniffi carries control and state while frames take a separate path (changed rows in one direct ByteBuffer). Reordering to the value-first loop is the owner's call (see Recommended Action).

### Minor
- **Watcher endpoint trust (security)**: any core client can write the push doc, so the watcher would POST to any URL it finds there (exfiltration, SSRF). Allowlist scheme and host from local config (`https://ntfy.example.org`), https only, no redirects, short timeout, size cap, plus a test with a foreign host. This one belongs with item 2 in the fix plan; it is small but not optional.
- **Changes view is not read-only**: `git status` takes `index.lock` and can break the agent's own git. Repo config can trigger fsmonitor, textconv and ext-diff. Untracked names starting with `-` become options. Use a fixed argv: `GIT_OPTIONAL_LOCKS=0 git --no-pager -c core.fsmonitor=false`, `--no-ext-diff --no-textconv`, `status --porcelain=v2 -z`, `--` before paths. This is rated below MAJOR because the code-execution vector runs as the same user the agent already is.
- **Heartbeat cost**: each `doc.set` rewrites `docs.json` (up to 1 MiB of layout), and the desktop refetches the layout on every doc event (`hc.rs:89`). Write only on change, or filter by name.
- **Losing phone identity on update**: a signing-key mismatch forces an uninstall, which wipes the Keystore key, machines and push registration. Derive versionCode from major/minor/patch with a test that it increases. Record the signing fingerprint in the repo. Keep an offline break-glass restricted key. Allow export and import of the machine list.
- **Web-push crypto**: use the UnifiedPush connector's built-in decryption and the `ece` crate rather than hand-rolling it. Keep the RFC test vectors.
- **Smaller spec gaps**:
  - Headless default size is 200x120 (`config.rs:41-42`); point to "Use phone size".
  - Detect a missing herdr-core by exit 127 plus its stderr text.
  - State the attach history value (desktop: 2000).
  - Define the agent display-name fallback (name, then app name).
  - Specify lifecycle when backgrounded.
  - Ghostty pin: `vt.rs` targets `291fd05` while the build uses `1e5cdb8`; regenerate the bindings and add a test.
  - `.gitignore` should cover the whole reference-shots dir.
  - Q1 is already answered by `ListResult`; keep only the stability question.

## Points of Disagreement

- **Severity of the untestable comparisons**: the Strategist rated this MINOR, the Engineer MAJOR. I rated it MAJOR: the owner's workflow turns each scenario into a test, so an unexecutable scenario blocks M2, not only polish.
- **Tailscale SSH vs OpenSSH**: the Adversary feared the forced command is never consulted because the fleet uses Tailscale SSH. The Strategist cited OpenSSH on WSL. The local setup settles it for WSL: Tailscale SSH runs only on other machines, and WSL uses OpenSSH. The Mac remains unverified, so the requirement stands as a per-machine check.
- **Grace delay**: about 20 s (Adversary) against 45-60 s (Strategist). Make it configurable with a default near 30 s, since the cost of a late alert is lower than the cost of a muted channel. Low stakes.
- **Alerting on startup**: the spec suppresses states present at start. The Adversary wants alerts for currently blocked terminals. I side with the Adversary, with alerts deduplicated through the persisted per-terminal record so restarts neither drop nor repeat alerts.
- **Changes git hardening**: the Engineer rated it MAJOR on security grounds. I downgraded it to MINOR: there is no privilege boundary between the agent and the phone's git (same user). Lock contention and option injection are real but cheap to fix.

## Risk Profile

1. **Silent alert loss** (likelihood 4 x impact 4). Trigger: distributor re-register or reinstall, wrong core under systemd/launchd, or unverified VAPID/binary body. Blast radius: the app's main purpose, with agents blocked for hours. Detection today: none. Mitigation: item 2 (delivery status, test-alert action, scoped write grant, `connect_existing`, early spike).
2. **Noisy and blind alerts** (5 x 3). Trigger: sub-agent turns, desk use, errors, watcher restart. Blast radius: alert fatigue, then a muted channel. Detection: owner complaint. Mitigation: item 3 (shared transition table, persisted state, grace delay, `cleared` push).
3. **Phone key becomes a shell** (3 x 5). Trigger: an sshd that ignores `authorized_keys`, an unlocked phone, or a signing-pipeline compromise. Blast radius: shell on the workstation and the Mac, reversing the clean-phone model. Detection: none in the spec. Mitigation: item 6 (refused-command scenario per machine, key auth decision, artifact-only signing, locked dependencies).

Also scored 12: upstream drift breaking "never resizes the Mac" (item 5), and identity loss on update (Minor).

## Blind Spots

- Accessibility (TalkBack, font scale on a terminal grid, contrast in the six themes): not examined.
- Doze, battery restrictions and Android 13+ notification permission for the UnifiedPush connector: touched only by inference.
- Mac side: Remote Login/sshd config and launchd watcher behaviour were not checked by anyone.
- The design canvas and comps were not opened, so visual scope was judged from the text alone.
- Upstream response timing: `decisions.md` says to ask the maintainers before writing code. No review weighed what happens if they say no to a client-claimed doc name or to viewer presence.
- Multiple phones or a replacement phone: only the Adversary's restore case touches it.
- russh signer API, connector API and Android 15 FGS limits were reviewed from memory, and the symbol check covered names only.

## Recommended Action

1. **Owner decisions** (one at a time, pick first):
   - (a) Reorder to the value-first loop. Pick: yes. It ends in the same place and delivers the useful loop sooner.
   - (b) Keystore user authentication vs background reconnects.
   - (c) Name an MVP cut (tiles, peek, rail, six themes and Changes are v1.x candidates).
   - (d) Ask the maintainers for viewer presence, a status hook, the doc-name namespace and upstreaming `herdr-proto`.
2. **The fix plan must address items 1-9 plus watcher endpoint allowlisting.** In order: doc names; the alert delivery and status path; the shared attention model; RPC semantics, timeouts and CREDIT; size and reattach rules plus the 0.1.15/0.1.16 matrix; signing and key hardening; lenient layout parsing; measurable test scenarios; M0 spikes (device smoke test, Keystore SSH, push end to end) and the uniffi frame path in `design.md`.
3. Verify the Mac's sshd and add the refused-command scenario before M1.4.
4. Send the fix plan to `project-scrutinizer`, scoped to these findings.
